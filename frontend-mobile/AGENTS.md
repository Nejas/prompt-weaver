# Правила мобильного проекта

## Порядок работы

- Перед изменениями описывать шаги, объяснять зачем и как они будут выполнены и ждать одобрения пользователя. Не приступать к изменениям до одобрения.
- Не запускать полную сборку проекта без отдельного разрешения пользователя. Согласовывать проверки, если они требуют такой сборки.
- Сохранять существующие изменения пользователя. Не менять зависимости, архитектурные решения или публичные контракты без согласования.

## Цель и платформы

Мобильный клиент платформы шаблонов промптов и адаптивного обучения разрабатывается на Kotlin Multiplatform для Android и iOS. Общий интерфейс создаётся на Compose Multiplatform. Веб-цель пока не входит в область проекта.

### Референс LibreChat

- Использовать [LibreChat](https://github.com/LibreChat-AI/LibreChat) как источник для изучения решений по чату, истории переписки и подключению моделей. При необходимости изучать актуальную документацию и исходный код конкретной версии.
- Адаптировать идеи к Kotlin Multiplatform, Compose, Decompose, Koin и контрактам нашего backend; не переносить архитектуру или код автоматически. LibreChat использует другой технологический стек и не считается частью этого приложения без отдельного решения.
- При заимствовании кода проверять условия лицензии соответствующей версии и сохранять необходимые лицензионные уведомления и сведения об авторах.

## Объектно-ориентированное проектирование

- Проектировать код с применением ООП и принципов SOLID: давать классам и компонентам понятную ответственность, зависеть от необходимых абстракций и сохранять корректность их реализаций. Создавать интерфейсы и абстракции, когда они решают практическую задачу.
- Для повторного использования и объединения поведения отдавать предпочтение композиции. Наследование применять, когда оно соответствует отношению «является разновидностью» и не нарушает поведение базового типа.

## Архитектура

- Использовать Clean Architecture: разделять Presentation, Domain и Data. Зависимости направлять внутрь: Presentation и Data зависят от абстракций Domain; Domain не зависит от UI, платформенных API, сетевых библиотек и деталей хранения.
- Строить проект многомодульно по функциям и ответственности. По мере появления функций выделять модули с явными публичными контрактами; новые модули и их границы сначала согласовывать. Не создавать пустые модули и не дробить проект без практической необходимости.
- Группировать код по функциям, например каталог, шаблоны, авторизация и чат. Структуру модулей определять по реальным задачам, а не копировать схему другого проекта без адаптации.
- В Domain размещать бизнес-модели, правила и необходимые сценарии использования; интерфейсы репозиториев определять на стороне потребителя. Не добавлять сценарии, которые только дублируют один вызов и не выражают полезной логики.
- Размещать каждую самостоятельную модель предметной области в отдельном файле с соответствующим именем. Повторяющиеся свойства и поведение обобщать, когда это отражает общую предметную сущность и упрощает код; не создавать абстракции без практической необходимости.
- В Data размещать сетевые и локальные источники, реализации репозиториев, модели передачи и преобразование их в модели Domain. Не передавать сетевые модели непосредственно в UI.
- Общий код, применимый на обеих платформах, размещать в `commonMain`. Платформенно-зависимые реализации размещать в соответствующих source set и предоставлять через общие абстракции.

## Структура модулей и их назначение

Следующая структура согласована как целевая для первого этапа. Сейчас проект содержит `androidApp`, `iosApp` и `shared`; остальные модули добавлять при реализации соответствующей функциональности, а не создавать заранее пустыми. Перед созданием модулей описывать изменения и ждать одобрения пользователя.

```text
frontend-mobile/
├── androidApp/                    # Точка входа Android
├── iosApp/                        # Точка входа iOS
├── shared/                        # Сборка приложения и корневая навигация
├── core/
│   ├── network/                   # Общая сетевая инфраструктура
│   └── ui/                        # Тема и общие UI-компоненты
└── feature/
    └── catalog/
        ├── domain/                # Модели и контракты предметной области
        ├── data/                  # Работа с API и реализации репозиториев
        └── presentation/          # Компоненты Decompose и экраны Compose
```

- `androidApp` и `iosApp`: платформенные точки входа и необходимые настройки. Общую логику приложения сюда не переносить.
- `shared`: связывание модулей, составление графа Koin, создание корневого компонента Decompose и корневая навигация. Платформенные точки входа запускают общую часть приложения с учётом жизненного цикла платформы.
- `core:network`: настройка общего HTTP-клиента, адреса Gateway и общих сетевых ошибок. Платформенные движки и специфичные настройки размещать в соответствующих source set.
- `core:ui`: тема, типографика и общие Compose-компоненты, не зависящие от конкретной функции. Выносить элементы при реальном повторном использовании или самостоятельной роли.
- `feature:catalog:domain`: модели шаблона, параметров и собранного промпта, контракт репозитория и необходимые бизнес-сценарии. Здесь нет UI, HTTP-клиента, платформенных API и деталей хранения.
- `feature:catalog:data`: вызовы HTTP API каталога и сборки, сетевые модели, преобразования и реализация контракта репозитория. Коды API и сетевые модели не передавать в Presentation напрямую.
- `feature:catalog:presentation`: компоненты Decompose, неизменяемые состояния и действия MVI, экраны списка и деталей шаблона, форма параметров и просмотр результата. Здесь использовать Domain и общие UI-компоненты.

### Направление зависимостей

```text
feature:catalog:presentation -> feature:catalog:domain
feature:catalog:presentation -> core:ui
feature:catalog:data         -> feature:catalog:domain
feature:catalog:data         -> core:network
shared                       -> модули, необходимые для сборки приложения
androidApp / iosApp          -> shared
```

Стрелка означает зависимость кода. Domain не зависит от Data и Presentation. Компонент Presentation получает интерфейс репозитория из Domain; при сборке приложения Koin связывает его с реализацией из Data и передаёт зависимость через конструктор. Компоненты Decompose создаются с учётом своего жизненного цикла; Composable-функции получают состояние и обработчики через параметры.

### Порядок добавления функциональности

1. Определить пользовательский сценарий и необходимые контракты backend; согласовать новые модули и зависимости.
2. В Domain описать необходимые модели и контракт репозитория. В Data реализовать получение данных и преобразование сетевых моделей; в Presentation добавить компонент Decompose и экраны.
3. Зарегистрировать реализации и фабрики в Koin, подключить экран к корневой навигации в `shared`, затем проверить существенное поведение изолированными тестами.
4. Для каталога сначала реализовать список, детали и форму параметров; сборку промпта пока оставить в `feature:catalog`. Выделять отдельную функцию промптов, если появятся самостоятельные сценарии вне каталога.

Авторизацию (`feature:auth`), чат (`feature:chat`) и обучение (`feature:learning`) проектировать и создавать по мере реализации. Чат зависит от появления серверного API обращения к модели. Безопасное платформенное хранение пользовательских токенов добавить при реализации авторизации. Не считать планируемые функции уже реализованными.

## Внедрение зависимостей

- Использовать Koin для создания и связывания зависимостей приложения. Объявлять зависимости и их области жизни в модулях Koin; общие и платформенные определения разделять по соответствующим source set.
- Внедрять зависимости в классы и компоненты Decompose через конструктор; не создавать внутри них конкретные реализации репозиториев, клиентов или других сервисов и не запрашивать зависимости из глобального контейнера.
- Собрать граф зависимостей в точках запуска приложения и передавать зависимости при создании корневых и дочерних компонентов Decompose. Учитывать жизненный цикл компонента и не делать всё общим экземпляром без необходимости.
- Переиспользуемые Composable-функции получают состояние, данные и обработчики через параметры, а не обращаются к Koin. Подменять зависимости в тестах через конструктор или тестовые модули Koin.
- Перед подключением Koin согласовать конкретную версию и проверить её совместимость с текущими версиями Kotlin, Android и iOS.

## Presentation: MVI и Decompose

- Использовать Decompose для компонентов экранов, навигации и управления жизненным циклом. Применять однонаправленный поток данных по принципам MVI: действие пользователя → обработка → обновление состояния → отображение UI.
- Состояние экрана представлять неизменяемой моделью и предоставлять через `StateFlow`. Действия пользователя представлять явно. Однократные события, например навигацию или уведомления, обрабатывать отдельно от постоянного состояния.
- Компонент Decompose управляет состоянием и вызывает сценарии Domain; Composable-функции отображают состояние и передают действия, не выполняя сетевые запросы и не храня бизнес-правила. Не вводить отдельный ViewModel параллельно компоненту Decompose без согласованной причины.
- Явно учитывать загрузку, успешный результат, пустые данные и ошибки там, где они применимы. Не скрывать ошибки и не отображать технические детали вместо понятных сообщений.
- Навигацию и жизненный цикл компонентов проектировать для Android и iOS; не предполагать, что поведение одной платформы автоматически совпадает с другой.

## Backend и данные

- Мобильное приложение взаимодействует с проектом через HTTP Gateway. Внутренние gRPC-сервисы, Bifrost и провайдеры моделей не вызываются мобильным клиентом напрямую.
- Использовать существующие контракты backend; изменение API согласовывать отдельно. Централизовать настройку адреса сервера и предусматривать различия адресов для эмулятора и устройства.
- Не хранить ключи провайдеров моделей, пароли или токены в исходном коде, ресурсах и логах. Для пользовательских токенов выбрать безопасное платформенное хранилище при реализации авторизации.
- Ввод пользователя остаётся данными; проверка параметров и применение правил выполняются backend. Клиент может предварительно валидировать форму для удобства пользователя.

## Код и интерфейс

- При создании UI использовать общую тему, токены и подходящие компоненты из `core:ui`. Не дублировать существующие компоненты и не задавать произвольные цвета, типографику, отступы и радиусы, если для них уже есть подходящие токены. Если общего компонента недостаточно, расширять его или собирать экран из существующих элементов с учётом практического переиспользования.

- Следовать существующим соглашениям Kotlin и Compose: понятные имена, небольшие функции и компоненты, отсутствие дублирования и лишних зависимостей.
- Проектировать Composable-функции переиспользуемыми: передавать данные и обработчики действий через параметры, не привязывать общие элементы к конкретному экрану и состоянию Decompose. Выносить компонент при реальном повторном использовании или очевидной самостоятельной роли, избегая преждевременных абстракций.
- Переиспользуемые цвета, типографику и компоненты оформлять централизованно. Поддерживать светлую и тёмную темы, читаемость и доступность. Конкретный визуальный стиль и палитра согласовываются с пользователем.
- Добавлять зависимости через каталог версий Gradle; новые библиотеки и их версии согласовывать и проверять на совместимость с Android и iOS.
- Не добавлять в пользовательский интерфейс технические детали, которые не помогают выполнить задачу.

## Тестирование

- Проверять бизнес-логику и состояния экранов независимо от сети и UI, подменяя внешние зависимости. Для сетевого слоя проверять существенные контракты, ответы и ошибки.
- При изменениях, затрагивающих обе платформы, учитывать Android и iOS. Указывать, какие проверки выполнены, а какие не удалось выполнить.
- Не писать тесты, которые лишь повторяют реализацию без проверки полезного поведения. Полную сборку запускать только с разрешения пользователя.

## Независимое ревью

- После реализации изменений в коде создавать субагента для независимого ревью результата, если такая возможность доступна. Попросить его проверить корректность, соответствие архитектуре и правилам проекта, возможные регрессии и существенные пробелы в тестах.
- Дождаться результата, самостоятельно проверить замечания и исправить подтверждённые проблемы в пределах согласованной задачи. Изменения, выходящие за согласованный объём, предварительно согласовать с пользователем. При необходимости повторить соответствующие проверки, не запуская полную сборку без разрешения.
- В итоговом ответе сообщить результат ревью и оставшиеся риски. Если субагент недоступен, прямо сообщить об этом и провести самостоятельную проверку.

## Коммиты

Использовать формат `type: short description`. Описание писать на английском языке, с маленькой буквы и без точки в конце. Применять `feat`, `fix`, `test`, `docs`, `refactor` или `chore` по смыслу изменений.
